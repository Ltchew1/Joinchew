Executive summary

The lifecycle underneath the portal is mostly real. Two seams aren't sewn shut yet.

Everything from Application through Payment Confirmation is genuinely built, tested against real Postgres, and already enforces "no blind payment" server-side. The gaps are specific and named below — they cluster at the two edges: the handoff into the portal (fires too early, and there's no read surface yet) and the handoff out of a completed engagement (service completion, Continuity, and graduate status have no tracked state at all). Neither is a redesign. Both are additive.

The single most important finding The Client Portal invitation (lib/clerk.js → createPortalInvitation) fires from api/send-decision.js at the moment an application is accepted — before a recommendation exists, before an agreement is signed, before a dollar has moved. This predates the Recommendation Engine and was never reconciled with it. A portal built today would need to represent a signed-in client who has no engagement, no agreement, and no payment yet — a state the portal has no vocabulary for, and this backend has no read API to describe (see §I).
What's already solid — don't re-litigate this Recommendation → Agreement → Signature → Payment is a real, server-enforced gate, not a UI convention. api/sign-agreement.js and api/create-program-checkout-session.js derive tier, price, and payment-plan terms entirely from the applicant's own engagement_selections row and the currently-active engagement_recommendations row — never from anything the client submits. A stale or superseded selection returns 409 RECOMMENDATION_UPDATED, not a checkout session. This has 180+ real-Postgres assertions behind it as of the last closeout pass.

Full detail — the stages with real substance

STAGE 3 / 4 / 5

Application → Admissions Review → Decision

Client-visible state
Nothing until decided — no status page exists between submission and decision (by design; there is no applicant-facing "your application is under review" screen, only the confirmation email at submission and the decision email later).
Admin-visible state
admin-applications.html — full pipeline queue with AI score, dimension scores, recommendation, rationale, one flag / one strength, internal note, applicant-facing message, all separated (internal never leaks — repo-wide grep-audited this pass and in an earlier pass).
Required emails
Applicant confirmation on submit; owner "new application" notice on submit; applicant decision email on decision.
Required authorization
Submission: none (public form). Review/decision: requireAdmin — real Clerk session verification, pinned to one ADMIN_CLERK_USER_ID, no RBAC.
Idempotency
api/send-decision.js checks status = 'decided' before acting — a repeat decision call returns alreadyDecided: true rather than re-sending or re-deciding.
What AI may recommend
lib/scoring.js — a 0–100 score across 4 dimensions and one of 5 recommendation labels, advisory only. It never reaches the applicant and never writes applications.decision directly.
What AI must never autonomously decide
The actual decision. api/send-decision.js requires an explicit human-submitted decision value — there is no code path where ai_recommendation auto-populates decision.
Failure/retry
Scoring failure is caught and stored as ai_error — the application still submits and can still be manually decided with zero AI input. Email failure inside decision-sending is not currently wrapped in a try/catch the way every other lifecycle email is (see Gaps §C-2).
STAGE 6

Recommendation

Entry / exit
Entry: application is accepted. Exit: admin clicks Approve & Send in the Scope Builder, creating a status='sent' row.
DB source of truth
engagement_recommendations — versioned, at most one sent and one draft row per application, enforced by partial unique indexes at the database level, not just application discipline.
Client-visible state
recommendation.html — primary tier, optional alternative tier (with a mandatory tradeoff explanation), CHEW's focus areas, "What Needs to Happen" (priorities + conditions), session cadence. A draft is never returned by the client-facing GET, by construction.
Admin-visible state
Scope Builder in admin-applications.html — full form when drafting/revising, read-only summary once sent, including notification-delivery status and a manual retry control.
What AI may recommend
Nothing. This is the load-bearing fact for the whole portal-readiness question: the commercial engagement recommendation is 100% admin-authored. There is no AI call anywhere in api/save-recommendation.js. The only AI touchpoint in the entire funnel is the admissions triage score three stages earlier.
Authorization
Write: requireAdmin. Read (client): access_token query param, no session.
Idempotency / notification durability
Sending is claim-before-send (client_recommendation_notified_at, separate from the sent_at DB fact) — an email-provider failure never blocks the recommendation from committing and is independently retryable via api/resend-recommendation-notification.js, never a duplicate send.
What the client can change
Nothing about the recommendation's content. They can request a scope review (durable, independently retryable notice to CHEW) or select among the offered tier(s).
What only CHEW can change
Everything about scope, focus areas, conditions, priorities, tier(s) offered — always via a new version once sent; sent content is immutable.
STAGE 7 / 8

Agreement → Signature

Entry condition
An active sent recommendation with no unsatisfied blocking condition.
Exit condition
A row in agreement_signatures bound to the exact recommendation id + version the client selected against.
Required payment state
None yet — signature happens before payment, always. This is already the directive's required sequence, verified server-side.
Security requirement
api/sign-agreement.js re-derives tier and price server-side from engagement_selections — it does not read tier/plan from the request body at all, even if a client attempts to smuggle one (directly tested: a smuggled tier field is silently ignored).
Failure/retry
A superseded recommendation (a new version sent after the client started this flow) returns 409 RECOMMENDATION_UPDATED rather than allowing a stale signature.
What must eventually appear in the portal
agreement_snapshot_html (the literal signed HTML), agreement_content_hash, signed_at, tier and payment-plan terms at signing — all already portal-safe, per §H below.
STAGE 10 / 11 / 12

Payment → Payment Plan → Enrollment

Entry condition
Valid, current, matching signature — re-verified server-side by api/create-program-checkout-session.js against the live recommendation/selection state, not trusted from the client.
Exit condition
Stripe's webhook confirms the event — never the browser's redirect back to booking-confirmed.html, which polls an authoritative status API instead of reading its own URL params.
Payment plan structure
Pay in Full (one charge) or Monthly (initial charge + N fixed installments via a Stripe Subscription Schedule) — same total price either way, timing only. end_behavior: 'cancel' means the schedule terminates itself at the agreed endpoint; verified no N+1 invoice is generated after the final installment.
Idempotency
Entry/checkout session ids are unique-constrained; a Subscription Schedule is created with an idempotency key (plan-schedule:<purchase_id>) so a redelivered checkout.session.completed can never create a second schedule; a redelivered installment event upgrades a 'failed' ledger row to 'paid' on the same invoice id rather than creating a duplicate.
Failure/retry
A declined installment sets payment_plan_status = 'payment_failed', notifies both parties once, and relies on Stripe's own automatic retry against the same invoice id — a later success on that id is treated as a genuine cure, not a new event, and does not re-notify.
Cancellation/refund
Not implemented as an operator action anywhere in this codebase. The agreement text describes refund/cancellation terms (Section 3.4/5 of lib/agreementText.js) but no API, admin control, or Stripe-side refund/cancellation flow exists to execute them. This is a real gap — see §C.
Required notifications
Customer + owner, separately, for: initial payment, payment failure, paid-in-full — each independently claim-before-send per program_purchases's six *_notified_at columns.
STAGES 13–16

Service/Capability Selection → Execution → Progress → Continuity

None of these four stages has any tracked backend state today — this is stated in the codebase's own PORTAL_INTEGRATION_REQUIREMENTS.md (§5, §6, §9) and independently confirmed here: no service_completed_at, no session-attendance record, no continuity_started_at/continuity_ends_at, no "capability selected/completed" record of any kind. program_purchases.status distinguishes pending_entry / pending_remainder / complete / active — none of which mean "sessions are being delivered" vs. "sessions are done." A client can be fully paid while the engagement is mid-delivery, or (rarer) fully delivered with a Monthly Plan still owing installments — the schema tracks the payment half of that split only.

STAGE 17

Expansion / Renewal

What exists
A client can receive a brand-new recommendation version at any time (admin-initiated, e.g. after a scope review) — mechanically identical to the first recommendation, fully versioned and tested. Membership exists as a separate, graduate-only continuity offer.
What doesn't exist
Any automatic or eligibility-checked path into Membership. lib/programs.js deliberately sets entryFeeWaivedForGraduates: false — not a bug, an honest placeholder, because there is no "graduate" determination available (depends on the missing service-completion tracking above). Every Membership signup charges the full entry fee today, to no one in practice, since Membership is unreachable through the current recommendation flow for a first-time applicant by design.
Core-principle check
This already satisfies the directive's explicit requirement — "Membership must NOT automatically continue at the original engagement price merely because someone completed an initial engagement" — trivially, because there is currently no automatic continuation of any kind. The commercial transition CHEW should design (§E) is the harder, better version of "trivially safe."

D · Launch blockers

What must be fixed before the portal can safely be built

Two items. Everything else in §C is real but does not block starting portal design work — it blocks specific portal features, which is different.

D-1 · Reconcile the portal-invite trigger (C-1)

Move it from decision-time to enrollment-time, or explicitly decide (and document) that early portal access is intentional and design the portal's empty/pre-payment state on purpose. Either is fine. Leaving it unexamined is not — it's the one place today where "the client is in a system" and "the client has a commercial relationship" are silently different facts.

D-2 · Build the portal read API (C-3)

PORTAL_INTEGRATION_REQUIREMENTS.md already specifies exactly what it must expose (§H below) and what it must never expose. No portal screen can be built against direct database access without re-deriving payment/agreement truth client-side — precisely the anti-pattern this entire engagement has spent its effort preventing on the marketing-site side.

Everything else — service completion, Continuity, graduate status, the Blueprint artifact, cancellation/refund, stale docs — should be scoped and prioritized, but none of them prevents starting the read API or the invite-timing fix.

E · Commercial architecture

Recommended pricing / payment / continuity structure

The directive asks CHEW not to force one price on everyone, not to invent bespoke pricing, and not to race to the bottom. The current 4-tier + admin-scoped-recommendation model already does this — the finding here is that it does it correctly, and the actual open question is Continuity, not tier pricing.

Why the current tier model already satisfies the core principle

Four fixed, published, non-negotiable tiers (Focused Builder $897 / Infrastructure $1,997 / Advanced Infrastructure $3,497 / Executive $4,997), each with a fixed deliverable, session count, and document-review allotment — and a human admin who reads the applicant's actual Starting Position and recommends the appropriate one, with an optional narrower alternative and explicit tradeoff language. This is exactly "starting position + needs + complexity → appropriate commercial recommendation," not a menu the applicant free-selects from and not a bespoke price invented per person. The recommended_priorities and recommendation_conditions fields already let CHEW explain, internally and to the client, why a given tier and scope were recommended — the "Recommended scope = X, Recommended price = Y, Reason = A/B/C" requirement in the original directive is already implemented, just not literally phrased that way in the admin UI.

What is genuinely missing: layer B Core Engagement (A) and Continuity (C) both exist as distinct commercial concepts. Service/Scope Components (B) — additional, individually selectable workstreams layered onto a core engagement — do not exist; the tiers themselves are the scope differentiation. Whether CHEW wants true modular add-ons (e.g., "add a second document-review event," "add an expedited-response upgrade") is a real product decision, not a technical gap — recommend deferring it until the portal surfaces real demand signal, rather than building a component catalog speculatively.

The Continuity transition — the actual hard problem

The directive is explicit: Membership must not simply continue the original engagement price. Today it doesn't, because Membership isn't reachable from the recommendation flow at all yet for a first-timer. The clean transition, once service-completion tracking (C-4) exists:

  1. Engagement ends — service_completed_at set by admin action.
  2. 30-day Continuity begins automatically — no charge, no re-engagement pressure, access to records preserved (already the locked doctrine per PORTAL_INTEGRATION_REQUIREMENTS.md §8).
  3. Membership is offered, never auto-enrolled — a distinct, affirmative opt-in at a distinct price ($147 entry, waived for graduates once C-6 exists; $97/mo recurring) that is explicitly not a renewal of the original engagement fee.
  4. No engagement fee ever silently recurs. One-time tiers stay one-time by construction — there is no subscription object anywhere in the one-time-tier checkout path (verified: it uses mode: 'payment', never mode: 'subscription', for all four one-time tiers).

The directive wants: Recommended for You / Included in Your Engagement / Available Next / Optional / Not Needed Right Now. Mapping the request onto what exists today:

Reusable mechanism, currently dormant A separate, pre-existing subsystem — capabilities, capability_provider_links, capability_relevance_rules, network_providers (documented in CAPABILITY_NETWORK.md) — already models exactly "what capability is relevant given a client's state, gated by an AND-chain of eligibility rules." Before building a new modular-service catalog for the portal, this is the mechanism to extend, not duplicate — but the two systems currently share confusingly similar names ("recommendation," "capability") for genuinely unrelated concepts, and that collision should be resolved in naming before either system grows further (C-10).

Who decides what's shown: per §A stage 6, 100% CHEW (admin), never AI, never the client's own free selection. This already satisfies "based on the client's approved situation... not simply what produces the largest sale" — there is no algorithmic upsell logic anywhere in this path.

I · Portal architecture dependencies

Everything the portal needs to consume, and in what shape

  1. One read API, not a database connection. The portal should never read Postgres directly — every field in §H should come through a purpose-built endpoint that applies the never-expose rules server-side, the same way api/recommendation.js already does for the client-facing recommendation page.
  2. A single "where is this client right now" status. Not scattered across five tables — one composed read that answers: accepted? recommendation sent? viewed? selected? signed? paid? plan status? engagement complete? in Continuity? Membership status? This is the literal backend equivalent of the portal's first-screen "you're in / here's what happens next."
  3. Auth model decision, explicitly not made here. Today's client-facing pages use a bare access_token query param (fine for a single-purpose page, not durable enough for a persistent portal session). The portal's own Clerk session is the natural fit — but linking a Clerk identity to an applications row (by email, presumably) is a real design decision with real edge cases (email changes, duplicate applications) that this report flags rather than resolves.
  4. Write-back routes through this backend, never forks state. Any portal-originated action (request a new recommendation, request Membership, eventually request cancellation) should call back into this backend's existing APIs rather than the portal maintaining its own copy of payment or contract truth.

M · Final build order

The sequence, not a list

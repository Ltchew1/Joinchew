Critical business rules

Checked against the actual code, not asserted

✓ Never charge before the agreement is signed — create-program-checkout-session.js requires a matching signature row.
✓ Never create an active engagement from acceptance alone — program_purchases only exists after checkout session creation, which requires signature + selection.
✗ Never invite into the portal merely because accepted — currently violated: this is exactly finding C-1/D-1. Fixed in §Enrollment rules.
✓ Never expose internal notes/AI rationale/admin data to clients — grep-audited twice this engagement, held both times.
✓ Never allow purchase outside the authorized engagement — server derives tier from engagement_selections, never the client.
✓ Never duplicate charge/enrollment/notification on replay — idempotency keys + claim-before-send columns, verified directly.
✓ Every commercial commitment has a durable source of truth — one authoritative row per fact, no browser-manufactured state.
✗ Every client-visible promise corresponds to an actual capability — Membership is client-visible (services.html pricing) but has no working purchase path. Not a promise-breaking bug today (no CTA points at it), but it is the gap §18 exists to close before Continuity can hand off to it.
✓ Every paid engagement has scope, price, structure, duration, and (as of this spec) a completion condition — the last piece is what §Completion adds.
✓ Situation-aware pricing without arbitrary bespoke pricing — 4 fixed tiers + admin-scoped recommendation, no manual price entry anywhere in the codebase.

Canonical commercial model

Locked — do not relitigate

Four fixed, published, non-negotiable one-time tiers (Focused Builder $897 · Infrastructure $1,997 · Advanced Infrastructure $3,497 · Executive $4,997), each with a fixed deliverable, session count, and document-review allotment. A human admin reads the applicant's Starting Position and recommends the appropriate tier (with an optional narrower alternative and a mandatory tradeoff explanation) — never an algorithm, never the applicant's own free choice from a menu. This is "starting position + needs + complexity → appropriate price," not a menu and not bespoke pricing, and it is already built and tested. No change proposed here.

Canonical pricing/payment model

Locked — do not relitigate

Pay in Full (single charge) or Monthly Plan (fixed initial payment + N equal installments via a Stripe Subscription Schedule, end_behavior: 'cancel') — identical total price either way. Verified: no N+1 invoice after the final installment, cure logic never re-notifies for a same-invoice retry success, idempotency key prevents a duplicate schedule on webhook replay. No new payment mechanism proposed anywhere in this spec — every new money-adjacent behavior below reuses this exact architecture.

Canonical agreement model

Locked — do not relitigate

Recommendation → Agreement (Deal Sheet, rendered before payment) → Signature, bound to the exact recommendation_id + version the client selected against, with an immutable HTML snapshot and content hash. A stale recommendation (superseded after the client started signing) returns 409 RECOMMENDATION_UPDATED rather than allowing a mismatched signature. No change proposed.

Canonical enrollment rules

The one rule that changes: who gets invited, and when

Rule

An application is "enrolled" the instant api/stripe-webhook.js confirms the first payment for that application's purchase — this already exists and is already correct. The portal invitation must move to fire from this exact event, not from api/send-decision.js's acceptance branch.

Specified change

  • Remove the createPortalInvitation call from api/send-decision.js entirely — acceptance no longer creates portal access of any kind.
  • Add a createPortalInvitation call inside api/stripe-webhook.js, at the same point program_purchases.status first transitions to complete/active — guarded by the same claim-before-send doctrine as every other webhook notification (a new portal_invited_at column, claimed before the Clerk API call, so a webhook redelivery never sends a second invitation).
  • No change to Clerk invitation mechanics themselves (lib/clerk.js is reused as-is).
Canonical service/capability model

Two different things were being conflated. Separating them resolves items 4, 13, 14, 15, and 23 at once.

The conflation "Service/capability" has meant two unrelated things in this codebase. engagement_recommendations / recommendation_conditions / engagement_selections is the commercial engine — what CHEW is paid to deliver. A completely separate, dormant subsystem — capabilities, network_providers, capability_provider_links — is a third-party referral registry (insurance, tax, legal, etc.), seeded with zero real providers by design. They share the word "capability" and nothing else. Item 13 ("service/capability selection data model") was at risk of being built by force-fitting the commercial engagement into the referral registry's tables. It should not be — they answer different questions.

Item 4 resolved: exact scope is already fully derivable — no new column needed

The chain already exists: program_purchases.agreement_signature_id → agreement_signatures.recommendation_id → engagement_recommendations. Every fact about what a client is entitled to — deliverable, session count, document-review allotment, focus areas, priorities, conditions — is already reachable by joining three existing tables. The fix here is not schema, it's a read composition: one query (or view) that resolves "this purchase's current entitlement" in one call, so execution tracking below has a single source to count against instead of re-deriving the join everywhere.

Items 13/14/15 resolved: a new, CHEW-internal execution ledger — not the referral registry

New table, modeled directly on the existing program_purchase_installments pattern (same one-row-per-event convention already proven in this codebase):

ColumnTypePurpose

purchase_idINTEGER REFERENCES program_purchaseswhich engagement this session belongs to

Table name: program_purchase_sessions. Document-review usage is lower-stakes and doesn't need a full ledger: a single document_reviews_used counter on program_purchases, incremented by the same admin action that logs a review, capped at PROGRAMS[tier].documentReviewEvents. Progress (item 15) is derived, not stored — sessions_delivered / sessionCount and document_reviews_used / documentReviewEvents are computed at read time from this ledger and counter; no separate "progress" table or percentage column.

Item 23 resolved: fix the name collision at the documentation layer, not the schema layer

Renaming either system's tables now is pure migration risk for zero functional benefit — nothing is currently broken by the shared vocabulary, the risk is entirely forward-looking (a portal UI surfacing both concepts to the same person). The fix: from this point forward, every new doc, comment, and portal-facing string refers to the commercial engine as "Engagement Recommendation" and the referral system as "Capability Network" or "Provider Match" — never the bare word "recommendation" or "capability" alone in client-facing copy. No table or column renamed.

Canonical completion/Continuity/Membership model

Items 16, 17, 18

Completion — item 16

New column: program_purchases.service_completed_at TIMESTAMPTZ, nullable, set only by an explicit admin action (never automatic, never inferred from sessions_delivered = sessionCount — a client can legitimately finish early or need a session added; completion is a human judgment call CHEW makes, not a formula). Setting it is idempotent: if already set, a repeat call is a no-op, not an error and not a second Continuity clock.

Continuity — item 17

Computed at the moment service_completed_at is set: continuity_ends_at = service_completed_at + interval '30 days', stored (not recomputed on every read) so it survives even if the tier's definition changes later. No charge, no automatic Membership enrollment, full record access preserved per locked doctrine. "Graduate" status (for the Membership fee waiver) is derived, not stored: EXISTS (SELECT 1 FROM program_purchases WHERE application_id = X AND service_completed_at IS NOT NULL) — a redundant stored boolean would only risk drifting from this one real fact.

Membership — item 18, the real finding

Membership currently has no live entry point create-program-checkout-session.js's tier === 'membership' branch is fully implemented and correctly gated against being reached by a first-time applicant — but nothing in the current site ever calls it. services.html shows Membership's real price with no CTA. engagement_recommendations's CHECK constraint excludes it from ever being recommended. There is, today, no button, link, or flow anywhere a graduate could click to actually buy Membership.

Specified fix: a new, narrow client-facing surface — reachable only once continuity_ends_at exists for that application (i.e., only during or after Continuity) — that offers Membership as an explicit, affirmative, separate purchase at its own price, with the entry fee waived if the graduate-derivation above is true. This is not a redesign of Membership's commercial terms (already correct, already locked) — it is building the front door that was never built.

Admin and client workflow

What each side sees, once this spec is built — website only, no portal screens

Admin (in admin-applications.html)

  • A "Mark Service Complete" control on any enrolled application, showing sessions-delivered / allotted and document-reviews-used / allotted at a glance before the admin confirms.
  • A "Log Session Delivered" and "Log Document Review" control, each capped at the tier's real limits — the UI cannot submit a number beyond what the tier allows.
  • Continuity/Membership status surfaced in the existing pipeline view: in delivery / complete, in Continuity until [date] / Member since [date] / Continuity elapsed.

Client (new page or extension of an existing one — still the marketing/commercial website, not the portal)

  • A status view (extending the existing token-based pattern, e.g. alongside recommendation.html) showing sessions delivered so far, out of the real total — not a percentage invented client-side, the same numbers the admin sees.
  • Once continuity_ends_at exists: an honest Continuity notice and, for the first time, an actual Membership offer with a real button.
Security boundaries

No new AI authority; two new admin-only writes

Every new write in this spec (mark-service-complete, log-session-delivered, log-document-review) is requireAdmin-gated, identical to the existing Scope Builder boundary. The client can only ever read their own entitlement/progress and select Membership when eligible — never write session counts, never mark their own engagement complete. AI has zero involvement anywhere in this spec; nothing here is a candidate for AI-assisted automation without a separate, explicit authorization.

Unresolved decisions

Genuine judgment calls, not technical gaps — need your answer, not mine

  1. Can an admin un-complete an engagement? (e.g., marked complete by mistake). Spec above treats completion as effectively one-way; if a correction path is needed, it needs its own rule for what happens to an already-computed continuity_ends_at or an already-sent Continuity notice.
  2. What happens exactly at continuity_ends_at? Spec above treats it as a quiet, no-action expiry (the relationship doesn't end, just the free window) — confirm this is the intended feel, versus an active "last chance" nudge, which would need its own reminder-cron entry.
  3. Does Membership eligibility require completion of this specific engagement, or any CHEW engagement ever? The graduate-derivation query above checks "any," which seems right for a returning client, but should be confirmed.
  4. Session/document-review ledger granularity — the spec above logs real dates and an admin identity per session; confirm this level of detail is wanted (vs. a simpler running counter with no per-event history), since the ledger is slightly more building than a counter for a feature that may only ever be admin-facing.
  5. Is a document-review "event" ever worth its own ledger (mirroring sessions) rather than a bare counter — only matters if the future portal needs to show which submission corresponded to which review, not just a used/total count.

Exact implementation order

Sequence, not a list

  1. Update or clearly mark historical the two stale docs (item 24). Zero risk, zero dependency on anything else, closes a real "contradictory information" gap immediately.
  2. Fix decision-email fault isolation. One try/catch in api/send-decision.js, isolated from everything else in this spec.
  3. Schema migration: the four new columns + program_purchase_sessions. Additive, idempotent, deployable ahead of any code that reads them — same discipline as every prior migration on this branch.
  4. Move the portal invitation trigger (remove from send-decision.js, add to stripe-webhook.js with its own claim column). This is the one item with real behavioral consequence — test it in isolation before layering anything else on top.
  5. Build api/mark-service-complete.js, api/log-session-delivered.js, api/log-document-review.js and their admin-applications.html controls.
  6. Build api/purchase-status.js — the read composition every subsequent client-facing surface (and, eventually, the portal) will depend on.
  7. Build the client-facing progress/Continuity status view on the website, reading from step 6.
  8. Build api/select-membership.js and its client-facing entry point — the Membership front door that doesn't exist today.
  9. Run the full adversarial test list above against real Postgres, matching this engagement's established testing discipline.
  10. Only then — with every state in §State machine backed by a real column, every new write idempotent, and Membership actually reachable — begin portal API design against a lifecycle that has nothing left to guess about.
